## 1. 已确认规则

| # | 规则 |
|---|---|
| R1 | **一家公司 = 一个公司库**。不存在同一公司的第二个库，也不存在个人空间、空间切换、空间回收站。“工作空间”只作为迁移期的底层存储名。 |
| R2 | **进入公司 = 公司成员资格**（在职且启用的公司成员）。不再由所有者逐账号“授权进入”。看到哪些模块仍由岗位权限决定，看到哪些记录由 §2 数据范围决定。 |
| R3 | **小组**：名称自定义；一个人可在多个组。左上角可切换“看哪一组”，并保留“全部”。切换只改变视角，不改变权限（权限永远是各组并集）。 |
| R4 | **小组协作范围以客户为准**：把客户放进小组，该客户的业务即由小组共同推进。 |
| R5 | **数据范围**：本人负责/经手 ∪ 所在小组 ∪ 部门领导看本部门及下级部门成员的业务 ∪ 总经理、老板、管理员与专业岗位（财务、QC、后勤、单证等）按模块看全公司。未入组只看本人。 |
| R6 | **档案是公司共享资料**：客户、供应商、产品/数字档案全公司可查（防重复建档、知道找谁对接）；敏感字段按既有遮罩。订单、报价、跟进、采购、履约等业务记录按 R5。 |
| R7 | **面料/成衣不再卡人**：业务员通用，可同时做面料和成衣。**主管按业务线划分管理权**：面料主管对全部面料订单、采购、开发、履约有管理权；成衣主管同理。 |
| R8 | 组长可选（10-19 定案不变）：首个生产案例不设组长，审批交部门领导或总经理；禁止自批。 |

## 2. 数据范围合成

```
可见业务记录(用户) =
    岗位为全公司范围（老板/总经理/管理员/专业岗位）       → 该模块全部
  ∪ 本人是负责人或经手人的记录
  ∪ 所在小组协作范围内的记录（§3）
  ∪ 作为部门领导：本部门及下级部门在职成员负责/经手的记录
  ∪ 作为业务线主管：本业务线的全部记录（§4）
```

- 业务记录的“负责人”以**客户跟进人/订单负责人**为锚，下游单据（采购合同、生产、质检、出运、单证、发票、收款核销、索赔）随所属订单可见，不各自判断。
- 模块权限先过滤（没有财务读权限的人，即使在组内也看不到收款）；数据范围只在模块内再按记录收窄。
- 动态、待办、通知、日历、附件、搜索、报表汇总、AI 助手读取，全部按同一结果裁剪；报表只统计可见记录。
- 写入 = 岗位写权限 ∧ 记录可见 ∧ 各业务规则（审批、禁止自批不变）。

## 3. 小组协作范围

### 3.1 以客户为准（R4）

最常用的条件是“某客户 · 全部”：该客户名下现有及以后新增的全部业务对组员可见并可协作。更细的组合见 §3.2。

### 3.2 组合范围（用户 2026-10-28 纠正：不是单笔，是灵活组合）

一个项目通常包含多笔业务；小组的协作范围由**若干条范围条件取并集**组成，每条条件可自由组合：

| 维度 | 取值 | 说明 |
|---|---|---|
| 客户 | 某个客户 / 不限 | 不限客户仅业务线主管、总经理/管理员可设 |
| 业务线 | 面料 / 成衣 / 不限 | 取自记录自身的类型 |
| 季节 | 如 SS27、AW27 / 不限 | 取自订单、报价、开发等记录的季节 |
| 供应商 / 工厂 | 某个供应商或加工厂 / 不限 | 命中该厂的采购/加工合同、生产、质检、收货；所属订单按 §3.4 规则 2 只读可见 |
| 手选业务 | 任意多笔订单、报价、开发案、商机 | 固定加入，可跨客户 |
| 排除 | 任意多笔 | 优先于以上条件 |

示例：「H&M · 全部」「H&M · SS27」「H&M · 成衣」「H&M · SS27 · 面料」「ZARA 的 3 个订单 + H&M · AW27」。

- **条件是动态的**：以后新增、且符合条件的业务自动进组（如 H&M 新建一张 SS27 订单）；季节或业务线改了，按新值重新判断。手选业务固定在组内，直到移出。
- **缺字段不猜**：没有填季节的记录不匹配季节条件；之后补上季节或转成有季节的订单时再匹配。
- **沿业务链延伸**：见 §3.4，任何一个节点进组，其后续整条流程自动在组内。
- **“项目”就是小组本身**：为一个季度系列、大单或专项建组并设置条件，结束后解散，历史留痕。不另建项目对象。
- **设置时即时预览**：编辑条件时显示当前匹配结果（如「订单 8、报价 3、开发 1」）及明细，保存前可确认；保存、修改、删除条件写审计。
- **组内新建**：左上角选中某组时新建业务，如果新业务已符合该组条件即自动归入；不符合时表单提供“加入当前小组”（加为手选业务）。
- 同一笔业务可同时属于多个组；条件移除或退组即时失效。

### 3.4 业务链连贯性（用户 2026-10-28 要求）

**原则：小组覆盖的是业务链，不是孤立单据。** 一个节点进组后，从它派生出的全部后续环节自动在组内，转报价、转订单、拆单、补单、售后都不会掉出小组。

**做法：不在单据上另存“所属小组”，每次读取时按现有来源关系实时推导。** 来源关系是唯一依据，所以转化、拆分、改来源后结果自动一致，不会出现“标签没跟上”。

#### 业务链节点与连接（按现有字段）

| 上游 → 下游 | 现有依据 | 状态 |
|---|---|---|
| 线索 → 客户 / 商机 | `lead.customerId`、`lead.opportunityId` | 已有 |
| 商机 → 开发案 / 报价 | 无 | **缺口：开发案、报价需增加可选“来源商机”，从商机发起时自动带入** |
| 开发案 → 版本、打样轮次、寄样、产品档案 | `devId`、`sourceDevId`、`sourceVersionId` | 已有 |
| 开发案 / 产品 → 报价条目 | 报价条目 `sourceDevId`、`sourceVersionId`、`productId` | 已有 |
| 报价 → 订单 | 订单条目 `sourceQuotationId`（可部分转、转多张订单） | 已有 |
| 开发案 / 产品 → 订单条目（不经报价） | 订单条目 `sourceDevId`、`sourceVersionId`、`sourceProductId` | 已有 |
| 订单 → 采购/加工合同、生产、质检、收货、库存、出运、报关单证、发票、收款核销、费用、退税、资金归属 | 各记录 `orderId` | 已有 |
| 订单 → 索赔 → 贷项 / 补货单 | `orderId`、`sourceOrderId`、`sourceInvoiceId` | 已有 |

#### 推导规则

1. **向下全覆盖**：节点在组内 → 它的全部下游（逐层）在组内，可协作。开发案进组，由它报出的报价、转成的订单、订单的采购到收款、售后补货全部跟随。
2. **向上只读**：在组内节点的上游来源（商机、开发案、报价）对组员只读可见，用于看样品标准、报价依据；**不顺着上游扩散到兄弟分支**（同一开发案给别的项目下的另一张订单，不因此进组）。
3. **订单整单为单位**：订单是履约最小单位；只要有一个条目来自组内节点，整张订单及其下游在组内，该单其他条目的来源对组员只读。
4. **条件按节点自身字段判断**：「H&M · SS27 · 成衣」匹配客户、季节、业务线都符合的开发案、报价、订单，再按 1–3 延伸。所以 SS27 开发案进组后，它转成的订单即使季节填错也仍在组内（来源在组内即在组内）；反过来季节符合的订单，即使来源不在组内也在组内。
5. **排除**：排除一个节点即同时排除只经由它进入范围的下游；被条件或手选直接命中的下游不受影响。
6. **跨链共用的单据**：一张出运、一次收款核销、一份对账单可能同时涉及组内和组外订单。组员可见该单据，但组外订单的条目、金额按不可见处理（只显示“另有 N 笔非本组业务”）。
7. **内部供料**：成衣订单使用另一张面料订单的内部供料时，组员可见供料分配记录本身（数量、状态、交期），不因此看到那张面料订单的完整业务。
8. **无客户的开发**（内部或备货开发）：不匹配客户条件，靠手选进组；之后报给客户的报价、订单按规则 1 跟随。
9. **同一来源的返单**：组内开发案以后返单（如 AW27 复单）默认也在组内，符合“链路连续”；不需要时把该返单排除。
10. **历史不丢**：订单取消、终止、关闭后仍在组内可查；移出条件或退组即时失效。

#### 校验（P3 测试必须覆盖）

- 开发案进组 → 报价 → 部分转两张订单 → 采购、生产、出运、发票、收款 → 索赔补货：每一步组员都可见，组外同事都不可见。
- 同一开发案的另一分支订单（不在组内）：组员不可见。
- 合并出运 / 合并收款：组员只见本组条目。
- 改来源、删条目、排除、退组后，下一次读取即按新关系生效。

### 3.5 一笔业务同时属于多个小组（2026-10-28 分析）

**允许，且是常态。** 例：客户 A 整户给「面料组 1」，也整户给「服装组 C」；A 的部分生产又在「某地某厂质检组」的范围内（按工厂条件）。范围由各组条件各自推导，互不影响。

| 方面 | 规则 |
|---|---|
| 可见 | 各组并集。一个人在多个组也只看到一份，不重复。 |
| 负责 | 小组不改变负责人。每笔业务只有一个负责人；小组是协作者。 |
| 能做什么 | 小组只放开“看得到哪些记录”，不放开模块。质检组成员仍只有 QC 岗位的模块：看得到该厂订单的质检、生产与必要的订单信息，看不到报价、成本、收款。 |
| 审批 | 不按小组走：按部门领导、业务线主管、总经理与禁止自批规则。若启用组长审批且申请人所在的多个组都有组长，不让系统猜，升到部门领导或业务线主管。 |
| 跟进、待办、附件、讨论 | 挂在业务本身，所有能看到这笔业务的人看到同一份；不建小组私有副本，避免各组信息分叉。 |
| 通知 | 按经办人、负责人、被指派人发，一人一条；不按小组群发。 |
| 统计 | 每个小组视角各自统计本组范围；“全部”去重；公司总数从不按小组相加。 |
| 标记 | 列表与详情显示“所在小组：面料组 1、服装组 C”；切换到某组时只看该组。 |
| 移出 | 从一个组移出只影响该组，其他组不受影响。 |
| 过宽提醒 | 设置“某客户 · 全部”时，预览按面料/成衣分开显示匹配数量；面料组拿到成衣业务时提示可改为「A · 面料」，是否改由设置人决定。 |

与业务线主管（§4）无关：小组是协作范围，面料/成衣主管的管理权按业务线，不按小组。

### 3.3 谁能管理

| 动作 | 允许 |
|---|---|
| 建组、改名、解散、加减成员 | 部门领导、业务线主管、总经理/管理员；启用的组长管本组成员 |
| 设置/修改范围条件 | 指定客户的条件：该客户负责人及其上级（部门领导、业务线主管、总经理/管理员）；不限客户的条件：业务线主管（限本线）、总经理/管理员。手选业务：该业务负责人及其上级。组员不能把别人的业务拉进组 |
| 组员 | 可见 + 按本人岗位权限协作（跟进、待办、经手办理）；负责人不因进组改变 |

## 4. 面料 / 成衣业务线（R7）

- 记录的业务线由记录自身决定：订单类型、开发案类型、采购/加工合同的业务域、内部发料域。客户不分线。
- **主管岗位**在账号上设置“管理业务线”（面料、成衣，可多选）。主管对本线全部记录可见，并有本线的审批、督办、改派、交接等管理权。
- 业务员不再设置业务组；经手人、负责人选择不再按面料/成衣校验。
- 现有“审批资格”（面料/成衣订单审批负责人、4 项供应商承诺审批人）保留按线配置，须与主管的管理业务线一致。
- 现状替换：公司库内的 `memberGroups`（面料/成衣业务组）退出，主管的管理业务线进入账号/岗位资料。

## 5. 左上角小组切换器

- 显示当前视角：某个小组 / 全部；未入组显示部门。
- 展开为轻量浮层：小组列表（名称、成员数）、“全部”、公司资料入口；有权者另有“管理小组”。
- 切换即时生效，不整页刷新：列表、首页、待办按视角筛选；选择记忆到个人偏好。
- 视觉与动效按当前 Mist 最高标准：浮层展开/收起、选中态过渡、键盘可达、减少动态效果时降级；实际浏览器同视口目视核对。
- 列表与详情：组内共享来的记录带弱化来源标记（小组名）；详情可看“共享至”的小组，有权者就地增减。

## 6. 实施分期

| 期 | 内容 | 验收 |
|---|---|---|
| P1 一公司一库 | 公司库按公司唯一（数据库约束+迁移前核对）；进入按公司成员资格；移除新建库、切换、回收站、逐账号授权进入；开户同时建库；本机演示保持一个演示公司 | 同公司第二个库无法产生；离职/停用即不能进入；越公司 404；既有数据不变 |

| P4 业务线主管 | 管理业务线设置；去掉业务员面料/成衣限制；主管按线管理 | 跨线业务员可办理；主管跨线无管理权 |
| P5 切换器与界面 | §5 | 浏览器实看，深浅色与常用宽度 |
| P6 真实走查 | 隔离租户按老板、部门领导、面料主管、成衣主管、业务员（组内/未入组）、财务、QC、后勤走一遍 | 如实记录未覆盖项 |

## 7. 当前实现（2026-10-28，main `e145e62`）

- 公司库：`MistWorkspace` 有 `companyId`，但不唯一；首次进入未被授权时会为个人新建一个库（`server/src/mist/repository.ts` `create`/`activeWorkspace`）；仍有新建、列表、回收站、`memberIds` 授权接口（`server/src/mist/route.ts`）。
- 读投影：`server/src/mist/access.ts` `projectState` 只按模块权限裁剪，模块内全公司可见；仅邮箱按个人隔离。
- 小组：人事 `Team/TeamMember` 只用于左上角显示（`organizationContext.ts`），不影响数据；`TeamDataGrant` 只接在旧客户档案服务。
- 面料/成衣：`state.memberGroups`（`server/src/shared/mistAccounts.ts`）限制经手人选择、主管团队视角与内部发料。
